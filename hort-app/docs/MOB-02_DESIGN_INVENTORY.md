## Inventário do frontend web

Fonte: código do repositório [vicentejuniordev/hort](https://github.com/vicentejuniordev/hort), commit `5620c24f604db63cd24129c99c09604599e823aa`, snapshot local consultado em `frontend/src/routes/AppRoutes.jsx`, páginas de acesso/cadastro e `services/authStorage.js`. O design visual deste PR segue o Figma fornecido, pois o web usa outra apresentação.

| Rotas web | Jornada observada | Destino no mobile |
| --- | --- | --- |
| `/`, `/selecionar-perfil`, `/login` | Entrada, escolha cliente/produtor e acesso | Boas-vindas, escolha de perfil e login nesta task |
| `/registrar-cliente`, `/registrar-produtor` | Nome, e-mail, telefone, senha, confirmação e termos; CNPJ no produtor | Cadastro real nas MOB-06/MOB-08, adaptado ao contrato Django |
| `/home-client`, `/view-horta/:id?` | Descoberta de hortas, produtos e planos | Catálogo de planos nas MOB-13/MOB-14; dados públicos de horta dependem de contrato |
| `/minhas-cestas` | Consulta das cestas | Assinaturas e agenda nas MOB-17/MOB-18 |
| `/perfil` | Perfil e dados pessoais | MOB-10, somente campos suportados pelo servidor |
| `/carrinho/:hortaId` | Carrinho e resumo | Venda avulsa fora do MVP; contratação de plano nas MOB-21/MOB-22 |
| `/mensagens`, `/mensagens/:id` e equivalentes do produtor | Chat | Fora do MVP |
| `/produtor`, `/produtor/gerenciar-planos`, `/produtor/perfil` | Resumo, gestão de planos e perfil | MOB-04/MOB-12/MOB-16/MOB-20/MOB-24, conforme contratos reais |

O acesso web usa contas locais em `localStorage` e aceita identificadores que não estão no contrato mobile. Esse mecanismo não foi portado. O app mantém login real por e-mail e consulta os perfis atuais em `/auth/me/`.

## Jornadas acordadas para o mobile

1. Primeiro acesso → boas-vindas → “Vamos lá!” → escolha cliente/produtor → cadastro em etapas → login. Nesta task, a escolha abre um aviso explícito de cadastro em breve e permite entrar com uma conta existente.
2. Conta existente → “Faça Login” → e-mail/senha → POST `auth/login/` → GET `auth/me/` → área autorizada. Conta com ambos os perfis conserva a entrada técnica existente; seleção final de modo é MOB-12.
3. Cliente autenticado → catálogo de planos → detalhes → dias distintos por cesta → revisão → contratação confirmada → assinaturas/agenda → cancelamento confirmado.
4. Produtor autenticado → produtos → planos → cestas/itens → prévia de valor → ativar/desativar oferta.
5. Conta → endereços, recuperação e exclusão, nas tasks previstas. Links de redefinição exigem o fluxo real e não são simulados aqui.

## Formulários e contratos

| Fluxo | Campos e comportamento |
| --- | --- |
| Login | E-mail e senha; teclado de e-mail, capitalização/correção desativadas, senha oculta, Avançar para senha e Enviar; validação local mínima e erros reais do servidor |
| Cadastro cliente (MOB-06) | Nome/e-mail/CPF/senha e endereço obrigatório. Enviar `password` e `password_confirm`; validar confirmação também no formulário e não presumir tokens no cadastro. Usar React Hook Form + Zod para etapas e validação de UX |
| Cadastro produtor (MOB-08) | Nome/e-mail/CNPJ/senha e endereço; produtor por CPF exibido em variantes do Figma exige decisão/contrato adicional |
| Endereço | No contrato atual: `rua`, `bairro`, `cidade` e `estado` (UF de duas letras), todos obrigatórios. CEP, número e complemento separados exigem evolução do contrato |
| Recuperação (MOB-09) | E-mail → link com uid/token → nova senha; falta referência visual específica no arquivo inventariado |

Credenciais permanecem apenas em memória nesta task. Não persistir senha. SecureStore/refresh/bootstrap/logout real pertencem à MOB-05. O formulário de login é o experimento nativo com estado local; a adoção de React Hook Form + Zod acompanha os cadastros em etapas, sem adicionar dependências sem uso agora.

## Diferenças entre design e domínio

| Referência | Decisão/limite |
| --- | --- |
| E-mail ou telefone; web também aceita CNPJ | Mostrar somente e-mail, suportado por `auth/login/` |
| Google, WhatsApp e Facebook | Manter imagens originais; ao tocar, avisar que o acesso ainda não está disponível, conforme escolha do responsável |
| Delivery e promessas de entrega | Texto de escolha de perfil apresenta planos; vínculo de endereço e operação logística ainda precisam de definição |
| Cadastro por CPF para produtor | API atual oferece CNPJ; nenhuma variante alternativa foi simulada |
| Fotos públicas, distância, avaliações e favoritos | Dependem de endpoints/dados adicionais |
| Carrinho/venda avulsa, chat, ganhos e entregas concluídas | Fora do MVP atual; não mostrar valores ou estados fictícios |
| Edição de nome/e-mail/telefone | `/auth/me/` é leitura e não tem telefone; contrato adicional necessário |
| Termos e privacidade | Faltam URLs/conteúdo aprovados; não inserir links vazios ou aceite sem documento real |
| Histórico | Distinguir dados atuais de composição/nomes de valor/programação preservados |

## Tema e componentes

Tokens em `src/shared/theme/tokens.ts`: primário `#2E7D32`, seção de login `#3BA55D`, botão do login `#00E91B`, campos `#C1BFEB`, fundo inicial `#FFFFFD`, fundo de perfil `#FAF9F6`, texto `#000000`/`#555555`. Poppins Regular/Medium/SemiBold/Bold e Istok Web Bold são empacotadas localmente.

Componentes criados: Button (normal/login/compacto, pressionado, desabilitado e carregando), Input (label/erro/ref nativa), PublicScreen (áreas seguras, teclado e rolagem), NoticeDialog, BackButton e SocialAccess. O Screen técnico da MOB-01 continua atendendo as áreas privadas provisórias; não houve redesenho dessas áreas.

Layout usa fluxo flexível e rolagem, com posicionamento absoluto somente para as ilustrações decorativas. As áreas de toque têm pelo menos 48 dp; os botões de perfil ficam visualmente mais altos que os 36 px do Figma. Em telas menores ou com fonte ampliada o conteúdo pode rolar. O teste nativo de teclado, leitor de tela e fonte ampliada depende da supervisão Android. O contraste dos textos pequenos branco/amarelo no verde do rodapé do login deve ser revisado com o responsável pelo design antes da publicação; as cores originais foram mantidas nesta comparação.

## Revisão solicitada pelo responsável

Após a entrega inicial, o responsável pediu para refazer o login. A nova composição usa fundo claro, verde escuro nos títulos, campos neutros com borda/foco, botão primário da marca e links verdes. Essa solicitação substitui a fidelidade visual ao nó `310:809`; boas-vindas e escolha de perfil conservam as referências originais. O novo login não usa o rodapé de texto branco/amarelo sobre verde apontado acima. Os controles sociais mantêm o aviso aprovado e a autenticação continua real.
